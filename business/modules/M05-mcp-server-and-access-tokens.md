# M05 Natural-Language Interface for LLMs: MCP Server and Access Tokens

Status in the app: not built yet. This page describes the module as the BRD defines it, then what the development build shows today.

## What it is for

Metis lets people work with it in natural language from the LLM tools they already use (assumption A-06). Each tenant gets its own remote server for the Model Context Protocol (MCP), which the BRD describes as the open protocol that connects LLM applications to external data and tools [Source: BRD v4.5 module M05, read 12 Oct 2026]. Any LLM client that implements the MCP specification can connect with a token or OAuth, and the clients that the provider has verified are listed in the connection guide (MCP-15). The server offers tools (functions the model can call), resources (read-only context such as a charter) and prompts (reusable request templates), and it always acts as the user who owns the token.

Connecting. Each tenant has one HTTPS endpoint (MCP-01). Users create personal access tokens with a name, scopes, an optional workspace or project restriction and an expiry within the tenant maximum; a token is shown once, stored hashed and revocable, and it shows its last use (MCP-02, BR-36). Clients that support MCP authorization connect through the platform's own OAuth authorization server with the user's consent, without copying a token (MCP-03). A page in the user's profile shows the endpoint, the connection, token creation, example client configurations, a test call and the tool list, and a failed test call names its cause and the fix (MCP-15). Tenant admins decide which clients may connect, which workspaces MCP may reach, the longest token lifetime and the scopes each role may grant (MCP-20).

What the server may do. Every request runs as the token's user: the effective permission is the intersection of the user's roles and the token's scopes, and tenant isolation applies (MCP-04). Read tools return figures computed by the platform with the BRD's metric definitions, so a figure matches the Overview screen for the same time, instead of raw rows for the model to add up (MCP-05, MCP-10). The tools that write are limited: appending journal entries and comments, and later updating WBS items, creating draft change requests and risks, and generating report drafts, all within baseline locks and version checks (MCP-06, MCP-07, MCP-14). Every tool belongs to one of four action classes (read, append-only, reversible write and prepare-only), which sets its safeguards, and an MCP write can be undone while its value is current (MCP-19). Governance stays with people: approvals, decisions, baseline application, deletions and changes of permissions or tokens cannot be executed through MCP. A tool can only prepare them and return a link for a person to confirm in the application (MCP-08, BR-35). Text stored in records comes back as data and is never read as an instruction (MCP-16).

Control and transparency. Every call is logged with the user, token, client, tool, a parameter summary, the result and the time; users see their own MCP activity and tenant admins see all of it (MCP-11). Limits and quotas apply per token and per tenant (MCP-12), tools return only the fields they need (MCP-13), and each tool has a stable, versioned contract (MCP-09). Resources and prompts (MCP-17) and a REST API with the same tokens, scopes, limits and audit (MCP-18) are priority P1. The BRD lists an indicative catalogue of 13 tool rows with their milestones and leaves the final names to the API design. The onboarding addendum adds a prepare-only setup tool group to the same server (ONB-07, [module M23](M23-onboarding-and-data-intake.md); [addendum section 7.1](../requirements/Enterprise_Portfolio_Intelligence_Governance_Platform_BRD_Addendum_Onboarding_v1.1.md#71-mcp-setup-tool-catalogue)).

Support for remote servers, OAuth and static tokens differs between LLM client applications [Unverified - confirm before applying], which is why the module offers both OAuth and personal access tokens (decision D-29).

Eighteen of the 20 requirements are priority P0. The release plan puts the module in milestone 1A, except the update tools (MCP-07) and the prepare tool of MCP-08, which arrive at 1B with the portfolio read tools (decision D-30; [BRD section 18.2](../requirements/Enterprise_Portfolio_Intelligence_Governance_Platform_BRD_v4.5.md#182-release-1-delivery-structure-d-01)). The BRD gives the module ten wireframe screens: 4, 5, 6, 8, 12, 23, 28, 33, 38 and 42, described in the [wireframe digest](../../design/wireframes/wireframes-digest.md). The [Connect an LLM through MCP](../journeys/connect-an-llm-through-mcp.md) journey runs on it ([BRD section 7.9](../requirements/Enterprise_Portfolio_Intelligence_Governance_Platform_BRD_v4.5.md#79-key-user-journeys)).

## What users can do today

Nothing yet. The app is not deployed and has no back end. Its development build runs on mock data and holds one screen of the BRD, the project overview (screen 24, [module M10](M10-project-overview-and-focus.md)), so no requirement of this module can be used.

The app has no MCP server, no connection page and no token screen, and it contains no MCP code. Screen 4 (the tenant admin's AI access) and screen 8 (the user's AI access) have no route in the app and no item in its navigation. Of the module's other wireframe screens, three have a route, and each link opens the page that says the screen is not built: screen 12 (the Governance tab of a project), screen 28 (a WBS item, which rows of the overview's lists link to) and screen 38 (Approvals in the sidebar). The AI copilot item of the sidebar belongs to [module M22](M22-ai-portfolio-copilot.md), a V3 feature: it is plain text tagged "Planned V3", not a link.

On the screen's side, the development build follows the rule that MCP-10 states for the tools. The overview screen draws only figures that a server sends, each with its as-of time and definition version, and computes none itself ([The app never computes a metric or a drill filter](../../architecture/decisions/metrics-are-server-snapshots.md), whose header lists MCP-10).

## Where the app differs from the BRD

None yet. Nothing of this module is built, so there is no built behavior to compare with the BRD.

## Open questions

- Should the MCP server keep no session, so that each request carries its own context? A reviewer proposed it, expecting it to suit the gateway and rate limiting better, and noted that the MCP specification of 2026-07-28 moves the protocol core to stateless requests [Unverified - confirm before applying]. The owner has not decided: the BRD still says "MCP session" in TEN-02 and in its isolation matrix, and the draft record [Each MCP request carries its own context](../../architecture/decisions/mcp-stateless-requests.md) keeps the proposal ([Pre-feasibility review of the BRD, round 1](../../history/reviews/metis-review-tien-kha-thi.md), lines 248 and 992 of the original).
- Which LLM client applications must be verified and listed in the connection guide, and do they connect with OAuth, static tokens or both? The BRD marks the support of each client as unconfirmed, and the answer drives MCP-15 and the choice of D-29 ([BRD v4.5, open questions](../requirements/Enterprise_Portfolio_Intelligence_Governance_Platform_BRD_v4.5.md#192-open-questions), Q-08, line 186 of [BRD part 04, roadmap and decisions](../requirements/source/parts/04-roadmap-decisions.md)). The first review asked which three MCP clients must be officially supported at launch ([Pre-feasibility review of the BRD, round 1](../../history/reviews/metis-review-tien-kha-thi.md), line 875 of the original).
- What must the audit log keep for MCP calls: parameter summaries only, or full parameters and results? MCP-11 logs a parameter summary and the result; the BRD weighs privacy against forensic value and records no answer (Q-12, line 190 of the same part 04).
