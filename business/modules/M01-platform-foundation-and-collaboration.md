# M01 Platform Foundation and Collaboration

Status in the app: not built yet. This page describes the module as the BRD defines it, then what the development build shows today.

## What it is for

The proof of concept that Metis grew from runs in one browser for one person: it has no accounts, and it keeps its data in the browser, at about 4.5 MB per project. This module turns that into a governed multi-user product. It holds what every other module relies on and what every user meets first: who they are, what they may see, that their work is saved, and how they hear that something needs them.

Sign-in and access. Users sign in with the methods their tenant enables, which [module M02](M02-tenant-and-subscription-management.md) sets (PLT-01), and a session lasts until it expires or the user signs out. Workspace owners invite members, give them a role and can deactivate them, and a deactivated member loses access at once but stays on history (PLT-03). When client access is approved, external users see only the projects they are invited to (PLT-02). Roles and record-level permissions are enforced on the server as well as in the screens, and a missing permission is always explained: no access, with an action to request it; read-only, with the reason (archived workspace, suspended tenant, frozen revision or locked baseline field); or session expired, with a way to sign in again without losing unsaved input (PLT-04).

Saved, shared work. All data lives on the server and edits autosave, with the save state shown in the same place on every editing screen (PLT-05). Several people can work on one project at the same time. Conflicting edits to one field are detected and never silently overwritten. One write contract serves the application, MCP and the API: each write carries the version of the record it was based on and an idempotency key, a stale version is rejected with the newer value, and a retried key is applied once (PLT-06). Files and each project's Docs & Links area sit in managed storage, with access control, time-limited download links and a malware scan (PLT-07, PLT-08).

Awareness and records. Notifications reach people in the application and by email for mentions, assignments, decisions requested or made, items due soon or overdue, and missing weekly status; approval requests cannot be muted (PLT-09). The audit log records configuration changes, baseline changes, approvals and governance decisions with the actor, the time, the values before and after, and the reason, and its entries cannot be edited or deleted (PLT-11). Search finds projects and WBS items within the user's permissions (PLT-12). A morning digest with Slack or Microsoft Teams delivery (PLT-10) and full-text search (PLT-13) come later.

Moving data and documents. A project or a workspace can be exported as a data file, and a project file can be imported as a new project that overwrites nothing (PLT-14). Deleting a project or clearing a workspace is limited to workspace owners, needs a typed confirmation and stays recoverable for a retention period (PLT-15). A PDF is a snapshot: it states its data as-of time, metric version and generator, and downloading it again returns the same file (PLT-16). Branded templates (PLT-17), personal preferences such as the display name and the default landing tab (PLT-18), a resettable sandbox workspace (PLT-19) and contextual help with a glossary built from Appendix A (PLT-20) complete the module.

Sixteen of the 20 requirements are priority P0, and PLT-10, PLT-13, PLT-17 and PLT-19 are P1. The release plan puts the module in milestone 1A, except client access (PLT-02), which comes at 1B if client access is approved ([BRD section 18.2](../requirements/Enterprise_Portfolio_Intelligence_Governance_Platform_BRD_v4.5.md#182-release-1-delivery-structure-d-01)). The BRD gives the module 18 wireframe screens: 1, 2, 3, 6, 10, 25, 33, 36 to 45 and 58, described in the [wireframe digest](../../design/wireframes/wireframes-digest.md). Two key journeys rely on it: in the [Approver daily round](../journeys/approver-daily-round.md) the requester is notified (PLT-09), and in [Tenant onboarding](../journeys/tenant-onboarding.md) the tenant admin invites users ([BRD section 7.9](../requirements/Enterprise_Portfolio_Intelligence_Governance_Platform_BRD_v4.5.md#79-key-user-journeys)).

## What users can do today

Nothing yet. The app is not deployed and has no back end. Its development build runs on mock data and holds one screen of the BRD, the project overview (screen 24, [module M10](M10-project-overview-and-focus.md)), so no requirement of this module can be used. There is no sign-in or account, no invitation, no saving, no file storage, no audit log, no export and no import.

The frame around screen 24 shows a few things in this module's area. They are read-only and fed by mock data:

- Navigation to the module's screens. Five of the module's 18 wireframe screens have a route in the app, and each route opens the page that says the screen is not built: screen 25 (the Charter tab of a project), screen 37 (the + New button of the top bar, which a phone does not show), screen 38 (Approvals in the sidebar), screen 39 (the notification bell of the top bar, which shows an unread count taken from the mock data) and screen 40 (the search boxes of the top bar and of the sidebar). The other 13 screens of the module have no route.
- Language. A select in the top bar switches the text of the app between English and Vietnamese.
- Save indicator. The project header of screen 24 shows "All changes saved" with a time taken from the mock data. Nothing can be edited.
- Help. At desktop width the top bar shows Help as plain text tagged "Planned V2". It opens nothing.
- No access and expired session. When the mock server answers that a project is forbidden to the demo user, the page shows a panel "You don't have access to this project", with a "Request access" action labelled "Not built yet". When it answers that the session ended, the page shows a dialog "Your session expired", with a "Sign in again" action labelled the same way. Only the mock scenario `sessionExpired` ends the session; the web build picks it with `?mock=sessionExpired` in the address. The third state of PLT-04, read-only, is not drawn.

## Where the app differs from the BRD

Nothing of this module is built, so there is no built behavior to compare with the BRD. Two features of the frame of screen 24 differ from what the BRD says of this module's area, each allowed by a decision record:

- Help. PLT-20 is priority P0 and asks for a help button on every screen that opens a searchable glossary. The shell shows Help as text tagged "Planned V2" at desktop width, because the help button and the glossary have no screen of their own yet. The record is [Final routes, drill filters in the URL, and unbuilt destinations](../../architecture/decisions/routes-and-unbuilt-destinations.md), whose consequences note that the help button and the glossary of PLT-20 may or may not get a screen.
- Interface language. No requirement of the BRD asks for a choice of interface language: its localization row covers workspace settings such as the time zone and the fiscal calendar, and dates and numbers in the user's locale, and the onboarding addendum says only that its cards, prompts and fixed reply are shown in the user's language. The app adds a select for English and Vietnamese, with one typed dictionary per screen ([Typed dictionaries per screen, English first](../../architecture/decisions/typed-dictionaries.md); the select itself is in [The language select on each platform](../../architecture/decisions/native-language-select.md)). The web build keeps the chosen language in the browser, because the app has no accounts yet, while PLT-05 puts all data on the server ([What the client remembers](../../architecture/decisions/client-memory.md)).

## Open questions

- Who sets the cadence of reminders for overdue items? PLT-09 notifies people of items due soon or overdue and lets each user choose the channel of notifications that are not mandatory, but no requirement says who configures how often a reminder repeats. The first review put this to the client together with the question of which notifications are mandatory beyond approvals ([Pre-feasibility review of the BRD, round 1](../../history/reviews/metis-review-tien-kha-thi.md), line 884 of the original, question 16 of its list of questions for the client).
- Is client access part of the first release? The BRD assumes a restricted Client role at milestone 1B, after a security review, and shares PDFs and reports until then (D-02, line 143 of [BRD part 04, roadmap and decisions](../requirements/source/parts/04-roadmap-decisions.md)); it asks whether the first users are internal PMs only (Q-04, line 182 of the same part). PLT-02 depends on the answer. The first review asked whether external users are a launch use case or can wait until after the internal pilot ([Pre-feasibility review of the BRD, round 1](../../history/reviews/metis-review-tien-kha-thi.md), line 874 of the original).
- Do the help button and the glossary of PLT-20 get a screen of their own? Until then Help is tagged "Planned V2", and the top bar shows it at desktop width only. Source: [Front-end foundation spec](../../history/specs/2026-10-05-frontend-foundation-spec.md), line 695 of the original.
- Where does the read-only state come from: which field of the API, and which reason code? PLT-04 lists an archived workspace, a suspended tenant, a frozen revision and a locked baseline field as reasons. The state is specified for the screen and is not drawn. Source: [Front-end foundation spec](../../history/specs/2026-10-05-frontend-foundation-spec.md), lines 293 to 297 and 703 of the original.
- Where do Request access and Sign in again lead, and is the wording of the states right? Both are text tagged "Not built yet", and the sentences are drafts until the owner reviews them. Sources: [Front-end foundation spec](../../history/specs/2026-10-05-frontend-foundation-spec.md), line 707 of the original; [Every response is validated, and every failure is a named state](../../architecture/decisions/validated-contracts-and-error-states.md).
