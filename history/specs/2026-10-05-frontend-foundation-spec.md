## 1. Goal, scope, success conditions

### 1.1 Goal

Build a front-end foundation that runs on web, iOS and Android from one codebase (FE-09), on
which a screen counts as done only when a machine can prove it is correct; then build exactly one screen,
`24-project-overview`, with every design detail, for the product owner to sign off (FE-03, FE-04).

### 1.2 In the first batch

- The Expo project scaffold, the test suites, the machine gates, the `pnpm verify` command, free CI.
- Design system: exactly the components that the application shell and the overview screen need.
- Application shell: sidebar, top bar, project header, tab bar.
- Project overview screen, API contract, mock data.
- Translation layer for English and Vietnamese, language selector.
- A generic "not built in the first batch" page for every destination that does not exist yet.

### 1.3 Outside the first batch

- Back-end, including the rules that compute metrics (FE-05, FE-10).
- The remaining 57 screens. The second batch (one screen per layout type and per shell) is planned only after
  the product owner signs off the first screen (FE-04).
- The other five shells: admin, vendor, no shell, external guest, onboarding.
- Release to the App Store and Google Play.

### 1.4 Conditions for signing off the first screen

1. The six gates of section 7 are green on every required platform.
2. Every gate of section 9 is green, including coverage, mutation testing, dead code, traceability.
3. Every reverse test of section 10 turns its own gate red.
4. `pnpm verify` is green on the Mac and CI is green on the same commit.
5. The tester has run the real-device checklist (section 11.3) and recorded the result.
6. Performance has been measured on one mid-range Android device and one iPhone, the figures recorded in section 12.
7. The product owner views the real screen in two languages, at three width levels, through every state,
   on web, iOS Simulator and Android, then signs off.

After sign-off, the screenshots of the screen on each platform and each width level become the baseline images.

## 3. Architecture

### 3.1 One app, folder layout (FE-06, FE-09)

```
apps/metis/
  src/app/                     Expo Router route files, which only wire up the shell and the screens
  src/core/                    plain TypeScript: API contract, client, translation layer, formatting, route table
  src/design-system/           base components, tokens.ts (generated), stories
  src/platform/                storage, API address, file download, external links, mock server startup
  src/shell/                   the application shell, and the part shared by every screen (see below)
  src/screens/24-project-overview/
    contract.yaml              screen contract (section 6)
    Screen.tsx                 the screen
    model.ts, model.<part>.ts  pure functions: API data into what the screen shows
    strings/en.ts, strings/vi.ts, strings/index.ts
  src/mocks/                   mock data and MSW handlers, used only in development and in testing
  e2e/web/                     Playwright
  e2e/safari/                  WebdriverIO with safaridriver
  e2e/native/                  Maestro flows, generated from the screen contract
  scripts/                     generators, gates, the verify command
```

No multi-package workspace, no path aliases (FE-06). Split a package when there is a second
place that uses it, for example a server.

`src/shell/` holds two roles (FE-27, as built). The first is the shell of every page: `AppFrame`
(it gathers the language provider, the workspace provider and the shell; the root layout and the tests attach to the same tree),
`Shell`, the sidebar, the icon column, the top bar, the drawer, the project header `ProjectHeader`, the
generic "not built" page. The second is the part that every screen shares: the data-fetching hook `useApi(key, load)` (it discards the
answer to an old query, with retry; the data hooks of the screens and of the shell are all this one), `problemOf` in
`model.problem.ts` (an API error into a state to draw), `StateView` (draws loading and error) and the dictionary of
the shell with the shared `states` block (section 5.5). A screen does not import another screen; what every screen needs lives in
`src/shell/`, and a new shared helper needs two call sites right in the change that adds it. A route file only
reads the URL parameters and hands them to the screen. Full conventions: `apps/metis/CONTRIBUTING.md`.

### 3.2 Boundary rules, enforced by ESLint

| Zone | Must not import |
|---|---|
| `src/core/` | `src/design-system/`, `src/platform/`, `src/shell/`, `src/screens/`, `src/mocks/` |
| `src/core/` and every model file (`model.ts`, `model.<part>.ts`) | UI or platform packages: `react`, `react-dom`, `react-native`, `react-native-*`, `@react-native*/*`, `@react-navigation/*`, Expo (`expo`, `expo-*`, `@expo/*`), MSW (`msw`, `msw/*`), whether by `import`, `import()` or `require`; no use of `window`, `document`, `localStorage`, `globalThis`, `self` |
| every model file | `src/design-system/`, `src/platform/`, `src/mocks/` |
| the model file of a screen | `src/shell/` (the screen composes the shell's model, the screen's model does not); inside the screen's own folder, only the `model.*` files and `strings/` may be imported |
| the model file of `src/shell/` | `src/screens/`, and every file of `src/shell/` except `./strings` |
| `src/design-system/` | `src/core/i18n/` (translation layer), `src/platform/`, `src/shell/`, `src/screens/`, `src/mocks/` |
| `src/screens/<id>/` | another screen |
| `src/shell/`, `src/screens/`, `src/app/` | `src/mocks/`: only `src/platform/` (mock server startup) and tests may import it |
| every file except `src/design-system/Text.tsx` and `Glyph.tsx` | `Text` of `react-native`; no file draws `Animated.Text`, because the design system's `Text` sets the typeface that each platform needs |

The rules apply to code that runs for real; tests may cross the boundary, for example to load `src/mocks/`. ESLint enforces them
with `import/no-restricted-paths`, `no-restricted-imports`, `no-restricted-syntax` and
`no-restricted-globals` in `apps/metis/eslint.config.js`; the ban lists are in
`apps/metis/eslint-rules/restrictions.js`, which has its own test; the reverse tests `boundary-*` and
`native-text` in section 10 prove that the rules know how to report red (FE-27, as built).

`src/core/` does not depend on the UI, so if a back-end or another app later needs the
API contract, it can reuse it whole.

### 3.3 Data flow

`Screen.tsx` calls the screen's hook with the workspace id and the project id; the hook calls the client in
`src/core/api/`; the client takes the absolute API address from `src/platform/config`, sends the request,
then checks the response against the zod contract. Valid data goes through `model.ts` into a
display model; the screen draws that model with design system components.

- Response 401: the session-expired state. Response 403: the no-access state.
- A response of the wrong shape: a clear error state with the name of the wrong field, never silently drawing
  the wrong data.
- The screen never counts or sums any row itself; every number is a snapshot returned by the server (MCP-10,
  FE-06).

### 3.4 Mock server (FE-05, FE-06)

- The MSW handlers and the mock data live in `src/mocks/`, shared by web (a service worker
  in development), Jest (`msw/node`), iOS and Android. On iOS and Android, the startup of the
  mock server in `src/platform/` is a layer that calls the handlers directly, with no network: the package
  `@msw/react-native` cannot be used (not on npm, its source fails to build, measured on
  05/10/2026). The screen does not change.
- Every web export uses `expo export --clear`: a trial measured that the release build carried the mock
  server along when exported right after a build with the mock server without clearing the cache.
- Three projects in the shell's tree are used to view the states (FE-07): Meridian CGI Campaign has full
  data per the wireframe of screen 24; Northwind Showroom VR has no baseline and has stale data;
  Spring Catalogue Renders returns 403.
- The release build does not contain `src/mocks/`; the dead code gate and a test on the web
  build prove it.

### 3.5 API contract of the overview screen

One call: `GET {apiBase}/workspaces/{workspaceId}/projects/{projectId}/overview`.
The response is validated with zod and consists of:

| Part | Content |
|---|---|
| Project header | its own contract `projectHeaderSchema` (`src/core/api/project.ts`): name, client, PM, phase (name, order, total), declared health, framework (name, version), baseline (version, date; may be empty), time of the latest save (for the shell's text "All changes saved · 09:41") |
| Metric snapshot | one snapshot per metric: metric id, value (or the state "not baselined"), data timestamp, definition version, freshness (`fresh`, `stale`, `partial`, `unknown`), drill-down filter (BR-32, BR-39), the filter values contain no comma |
| Breakdown | by status, by Category, by person in charge (each person with initials sent by the server) |
| Attention lists | upcoming milestones and gates, overdue, high and critical risks; each row has an item id, a WBS label, a number of days; each list carries a total and the first few rows, and the number of rows never exceeds the total (added at build time on 06/10/2026, so that the "more" part never shows a negative number) |
| Computed health | level and reason for each dimension (delivery, risk, resources, finance). First batch (foundation plan, 06/10/2026): the overall level, and the reasons for delivery and risk as on screen 24; the level of each dimension and the reasons for resources and finance wait for the BRD to define them (section 13) |

The response carries the workspace's IANA time zone (`timeZone`); every time on the screen is shown in this zone,
because BRD 12.1 computes "today" in the workspace time zone (added when writing the foundation plan on
05/10/2026). Timestamps are UTC times with a trailing Z.

As built (FE-27): every contract of a project page extends `projectPageSchema` of
`src/core/api/project.ts`, which holds the time zone (`timeZone`, zod rejects a zone that `Intl` does not know) and the project
header (`project`, the `projectHeaderSchema` contract); the overview screen's contract is
`projectPageSchema.extend(...)`. Thanks to this, each later tab (Charter, WBS, Plan...) draws its header and times
from its own response, without needing the overview screen's response; each page reports its tab and the header
marks that tab.
A person's initials (the shell's user, each workload-by-person row) are sent by the server, the app does not
compute them itself, because no client rule is right for every name order. The values of the drill-down filter contain no
comma: a link joins several values with a comma (`risk=high%2Ccritical`) and the target page splits there,
so the contract rejects a value that contains a comma.

The data carries only codes and user content; the display label of a code lives in the dictionary of
the screen (section 5). The detailed shape is written in `src/core/api/` at the build step; this contract is
what is handed over to the back-end (FE-10).

## 5. Visuals, fonts, brand, translation layer

### 5.1 Token

- `brand/tokens.css` is the only source of every shape and color number.
- `scripts/gen-tokens` reads that file and generates `src/design-system/tokens.ts`; the mode
  `--check` regenerates and then compares the difference. React Native cannot read CSS variables, so this is the
  only generator needed. Corrected against decision log section 8.6 ("drop the theme generator"): that
  holds for Tailwind on web, and no longer holds when styles are written with `StyleSheet`.
- Three groups of tokens do not become values used directly in components: the focus ring, the seven
  status color groups (used only through the status chip component), the chart palette (used only through the
  chart component).

### 5.2 Logo and icons

The logo is a component drawn from the original SVG file in `brand/logo/`, copied byte for byte into the app with
a byte-for-byte comparison gate; never write the word "Metis" in a font where the logo is needed (style guide
2.3). The favicon and the app icon come from the same folder.

### 5.3 Language selector

Shows each language's name in that language itself: "English", "Tieng Viet"; English by default.
On web it is a labeled `select` tag; on iOS and Android it is the platform's native picker
(`@react-native-picker/picker` states support for Android and iOS, not web). The choice is stored through
`src/platform/storage`; the `lang` attribute of the web page is set before the first paint; switching the
language changes the text at once.

### 5.4 Fonts

Newsreader, Inter, Manrope, self-contained in the repo, with no call to Google Fonts at run time. The files cover
the full Latin and Vietnamese character sets on every platform: on web it uses the `latin` and `vietnamese` blocks of
Google Fonts, chosen by block name (taking the first file takes `cyrillic-ext` by mistake, measured);
on iOS and Android it uses the full-character files because there is no mechanism to split into blocks. Newsreader uses the correct
optical size for the size-30 heading (the style guide loads `opsz,wght@6..72,500`). The licenses of the three
typefaces are recorded in `apps/metis/LICENSES.md` [Unverified until recorded].

### 5.5 Translation layer (FE-08)

- Each screen and the shell has `strings/en.ts` (the original), `strings/vi.ts` and `strings/index.ts`; the type
  `Dictionary<typeof en>` of `vi.ts` turns a missing, extra or misplaced key into a compile error.
  `strings/index.ts` exports `STRINGS` (a `{ en, vi }` record, of type `Record<Locale, ...>`) and `SAME_IN_VI`
  (the keys whose Vietnamese version keeps the text unchanged, such as the product name, project terms, separators,
  symbols and templates that hold only placeholders).
- Do not merge dictionaries across screens, do not use an English sentence as a key. The text of the error states lives
  once in the shared `states` block of the dictionary of the shell (FE-27): no access, not found, session
  expired, data of the wrong shape, server not responding, "Try again", "Back to {destination}". Each screen writes only
  its loading sentence (`states.loading`) and the title of the server-not-responding state
  (`states.unavailable.title`); `problemOf` (`src/shell/model.problem.ts`) builds the state from the API error
  and those two things.
- Do not assemble sentences by concatenation (FE-27): each sentence is a template with a `{name}` placeholder in the dictionary, filled
  by `interpolate` (a missing value is an error, `{name}` is never shown on the screen), because word order in each
  language differs; singular and plural forms go through `plural()` with two forms `one`, `other` (enough for English and
  Vietnamese; a language that needs more forms will need `Intl.PluralRules`); a list goes through `joined()` with the pattern `{list}, {item}`
  of each language, and an empty list is a type error. Lint enforces: in model files there is no string
  containing whitespace or punctuation, no `+` with a string, no `.join()`; no component of the design
  system, the shell, a screen or a route types text that users read (JSX text and props such as `aria-label`, `label`,
  `placeholder`, `title`).
- Dates, times, numbers, percentages are formatted with `Intl` according to the language. The formatting test runs
  on every platform because Hermes uses the operating system's data and has gaps on Android 7 to 11.
- Percentages are rounded down to an integer (FE-20, 06/10/2026): a project with work left never
  shows 100%; 99,5% shows 99%.
- Design system components receive all text through a required prop, with no default text.
- Dictionary test driven by a registry list (FE-27): `src/core/i18n/dictionaries.test.ts` keeps a
  list of every dictionary (folder, `STRINGS`, `SAME_IN_VI`) and goes red when a `strings/` folder of `src` is missing
  from the list; for each dictionary it checks that each language takes exactly the file bearing its own name, and the Vietnamese
  version has every key, the same placeholders, and no sentence still in English outside `SAME_IN_VI`. A new dictionary adds
  one line to that list.
- Adding a language (as built): add the code to `LOCALES` and the self-name to `NATIVE_NAMES` of
  `src/core/i18n/locale.ts`; a strings file next to each `en.ts`, of type `Dictionary<typeof en>`; one entry
  in the `STRINGS` record of each `strings/index.ts` (of type `Record<Locale, ...>`, so a missing one is a
  compile error); one entry in the list of the script that sets `lang` in `public/index.html`, because that script runs
  before the app loads.

## 6. Screen contract

`src/screens/<id>/contract.yaml` is the artifact a reviewer reads to learn what the screen promises, and is
the source that the test suites read.

```yaml
id: 24-project-overview
route: /w/{workspaceId}/projects/{projectId}/overview
shell: app
requirements: [OVW-01, OVW-02, OVW-03, OVW-04, OVW-05, BR-24, BR-32, BR-39]
title: { key: title }
elements:
  - id: tile-blocked
    role: link
    nameKey: tiles.blocked
    effect: { kind: route, to: 26, search: { status: blocked } }
  - id: scope-mine
    role: tab
    nameKey: scope.mine
    effect: { kind: url, search: { scope: mine } }
  - id: status-table-view
    role: button
    nameKey: status.tableView
    effect: { kind: state, attribute: data-view, from: chart, to: table }
states: [default, loading, noAccess, sessionExpired, readOnly, notBaselined, stale, invalidData]
responsive: { desktop: two-column, tablet: two-column, phone: single-column }
```

- Four kinds of effect, and only four: `route` (go to a screen by the manifest's screen id), `url`
  (write a query parameter), `panel` (open a dialog or a drawer), `state` (change an attribute
  on the screen). A control that cannot declare its effect is not yet allowed to be built.
- The behavior test suite on web and Safari reads the contract directly at run time; Maestro flows are generated from
  the contract, with a `--check` mode.
- Reverse check: every control found in the content area must be in `elements`.
- The example above only illustrates the shape; the full list is written at the build step, following section 4.3.

## 7. The six gates of the screen, on every required platform (FE-08, FE-14)

| Gate | Web (Chrome, WebKit, real Safari) | iOS and Android |
|---|---|---|
| Token | A dedicated lint rule: no number and no color code written directly in a style; only through `tokens.ts`. The rule applies to the properties size, spacing, corner radius, font size, line height and color; it does not apply to unitless properties (`flex`, `opacity`, `zIndex`) and to the border of 1 per style guide section 5. The only exceptions are the two kinds in the style guide (the intrinsic size of a drawing, the minimum width of a table column), each place marked with `// token-exception: <reason>`. Plus `gen-tokens --check` | The same rule, the same code |
| Shape | Playwright measures the DOM tree against numbers read directly from `brand/tokens.css`: sidebar 232, top bar 52, page margin 24, list rows from 44, metric tile figures 28, heading 30; three widths; no horizontal scrolling | Component tests require the drawn style to match the tokens; Maestro screenshots are compared with the baseline images after sign-off |
| Behavior | Playwright and WebdriverIO read the contract, click each control, measure the effect; the reverse check; every link of the shell opens a page that has a title; the browser console is free of errors | Maestro flows generated from the contract, tapping each control, measuring the effect |
| Translation | No sentence of `en.ts` is still shown after switching to Vietnamese; `lang` is correct; the choice persists after a reload; the layout does not break | As on web, measured with Maestro and component tests |

## 9. Testing system and code leanness (FE-12, FE-13)

### 9.1 Rule: a line of code gets in only when a machine can prove it is needed and correct

1. A test runs through it: 100% line and branch coverage; exclusions only through a list with a reason
   for each entry.
2. The tests really catch bugs: mutation testing with StrykerJS reaches the threshold in section 12.
3. It has a use: Knip (unused files, exports, dependency packages); a script for dictionary keys that are not
   read; a script for tokens that are not used, except for a debt list that may only be shortened.
4. If it is a control, it is in the screen contract.
5. Traceable: every requirement id in the contract's `requirements` has at least one test
   carrying that id in its name.

In addition: strict TypeScript (unused variables and parameters are banned); ESLint with boundary rules
(section 3.2), a cap on function complexity and file length (section 12), every time a rule is disabled it must record its
reason; Prettier.

### 9.4 Rules for tests, retyped text and language (FE-27, as built)

The full conventions, with examples, are in `apps/metis/CONTRIBUTING.md`; this section records the part a machine enforces.

- Test layers: the design system proves the look of a component; screens and the shell prove what they
  put into components (content, links, roles, accessible names, the layout they set themselves), finding
  elements through `testID`. A test of a screen or the shell does not re-assert the design system's styles and does not walk
  the element tree (`.parent`, `.children`, child indexes); a design system test may walk the tree of
  its own component. To prove what a block hands to a design system component, the test wraps
  that component in a pass-through spy (`jest.fn(actual.X)`): the real component still renders, and the test reads the props it
  receives (`src/spy.test.helper.ts`). Each screen has a data variant in which every numeric field is different
  (`distinct(data)`), so reading the wrong field goes red; a "must not be shown" test uses exactly the expression of
  its positive test; a wait time is never an assertion. The shared test builders are
  listed in `CONTRIBUTING.md`, section Tests.
- Retyped-text rule: `local/no-restated-literals` (`eslint-rules/no-restated-literals.js`, in
  `gate:lint`) applies to the tests of `src`, the specs of `e2e` and the `node --test` tests of `scripts/` and
  `eslint-rules/`. It rejects a string equal to a value of `src/mocks/fixtures/*` or of a dictionary,
  a string containing an identifier of `src/mocks/fixtures/ids.ts` (in a path or a `testID`), a
  string containing such a value that is at least two words long, and a string that fills a dictionary template whose fixed
  text part is at least two words; `'a ' + 'b'` counts as `'a b'`. A hand-typed English sentence may serve as the reference only in one
  model test per zone, `src/screens/<id>/model.test.ts` and `src/shell/model.test.ts`, where it
  proves that the model assembles sentences; there the rule checks only the mock data. The line right above a string is exempt when it
  holds `restated-literal: <reason>`. A lowercase ASCII word or camelCase, a string under four characters, a number,
  a regular expression and a template with an expression are outside the rule's reach; the reviewer checks that part. The paths
  of e2e are built from `ROUTES` and `IDS` (`e2e/web/paths.ts`).
- Language gate `gate:language` (`node scripts/check-language.mjs`): code, comments, test names,
  lint messages and the output printed by scripts and gates are in English; Vietnamese only in the dictionaries
  `src/**/strings/vi.ts` and on the line right after a comment `lang-exception: <reason>`; any other letter outside
  ASCII is an error (`non-ascii-letter`). In comments, test names and every Markdown line of the app,
  the gate also rejects references a maintainer cannot open: plan decision ids, task numbers, spec
  section numbers, wireframe line numbers, dates; BRD requirement ids (`OVW-01`, `BR-24`) are kept. When no
  path is given, the gate scans the app, `.github/workflows` and `brand/`, except `brand/style-guide.md` (the product owner's
  Vietnamese document).
- No test is switched off: lint rejects `only`, `skip`, `todo`, `fixme`, `fail`, `failing` (and other
  names such as `fit`, `xit`) in the tests of `src`, `e2e` and `node --test`; the `forbidOnly` of
  Playwright stops a run that has a test selected on its own; only the self-test of the browser guard
  (`e2e/web/test.spec.ts`) may call `test.fail()`. Every browser spec takes `test` and `expect` from
  `e2e/web/test.ts` (lint rejects `@playwright/test`), so a request that leaves the mock server or an
  undeclared page error turns the test red.
- Rule 5 of section 9.1, as built: `gate:trace` counts only tests that really run (not skip, fixme or
  fail; the name of a `describe` is only a prefix of the tests inside it), and only inside the folder of the
  screen itself (`src/screens/<id>/`, `e2e/web/<id>/`); an id that the contract additionally lists under `web` needs a browser
  spec in `e2e/web/<id>/`, because only a browser lays out the web page.
- Test-count floor: `gate:unit` and `gate:web` go red when a test is skipped or flaky, or when the number of
  passing tests differs from the number recorded in `scripts/test-floor.json` (an exact floor; a change that adds or removes a
  test updates it); `gate:web` also goes red when the number of runs that must fail (the guard's self-tests) differs from
  `webExpectedFailures`.

## 10. Reverse tests

Each gate has a deliberate breakage that proves it knows how to report red, except a gate whose reason is recorded in the list
`NO_CANARY` (below). `scripts/canary <name>` runs the gate
first and requires green, then breaks it, runs the gate again, requires red exactly because of the introduced defect, then restores the original state whatever the
result (the green baseline step was added at build time on 06/10/2026: if the gate is already red, the later red does not
prove anything about the introduced defect). Reverse tests are not in the suite
of unit tests because many need a browser or an emulator.

| Breakage | Gate that must go red | Test as built (FE-27) |
|---|---|---|
| Write a number directly into a component's style | Token | `token-literal`, `style-constant`, `style-unitless` (`gate:lint`) |
| Change a number in `brand/tokens.css` without regenerating | Token (`gen-tokens --check`) | `token-stale`: adds a line to `tokens.ts`, so the file drifts from the generated version (`gate:tokens`) |
| Regenerate the tokens with a number changed, code unchanged | Shape | not built, left for plan C |
| Delete the path of a navigation item | Behavior | not built, left for plan C |
| Add a button not declared in the contract | Reverse check | not built, left for plan C |
| Delete a Vietnamese sentence | Translation (compile) | not built, left for plan C |
| Replace the logo with text | Brand | not built, left for plan C |
| Shrink a button below 44 | Accessibility | `touch-target`: a 30 px control on screen 24 (`gate:web`) |
| Use a web API that Safari does not yet support | Browser compatibility | `compat` (`gate:lint`) |
| Add an export that nobody uses | Dead code | `deadcode` (`gate:deadcode`) |
| Add a function with no test | Coverage | `coverage` (`gate:unit`) |
| Delete an assertion in a test | Mutation testing | `mutation`: a test that asserts only the type of the result (`gate:mutation`) |
| Add a heavy loop in a component | Component performance | not built (Reassure not there yet), left for plan C |
| Add a large library to the web bundle | Web performance | not built (Lighthouse CI not there yet), left for plan C |
| Remove the requirement id from a test name | Traceability | `trace`, `trace-web` (`gate:trace`) |

The list as built is in `apps/metis/scripts/canaries.mjs`: 37 reverse tests for 11
gates. Besides the rows above there are: `unused-local`, `route-types` (`gate:types`); `prettier`
(`gate:format`); `language`, `language-date` (`gate:language`); `tooling` (`gate:tooling`); and for
`gate:lint`: `complexity`, `max-lines`, `disable-reason`, the boundaries of section 3.2
(`boundary-core`, `boundary-design-system`, `boundary-core-package`, `boundary-model`,
`boundary-screen`, `boundary-mocks`, `boundary-globals`, `native-text`), hard-coded text
(`default-text`, `shell-text`, `branch-text`, `model-text`), retyped text (`restated-literal`,
`restated-phrase`), disabled tests (`disabled-test`, `inverted-test`) and the guard of the browser specs
(`e2e-guard`). `NO_CANARY` in the same file records the reason for the two gates without a reverse test: `gate:deps` (the breakage
would have to install a package with a vulnerability or a wrong license, rewriting `node_modules` and the lockfile;
`scripts/check-licenses.test.mjs` proves the license rule knows how to go red) and `gate:native` (each run needs
a Release build and a booted iOS simulator; its flow was proven red once with a
wrong `testID` planted in). `gate:tooling` goes red when a `gate:*` script of `package.json` has no reverse
test and no reason in `NO_CANARY` either, or has both. `pnpm canary all` runs them all.

## 11. Where it runs (FE-15)

### 11.1 Free CI: GitHub Actions on Linux machines

Runs everything that does not need macOS: static checks, dead code, unit and component tests on four platforms, the data
contracts, mutation testing on changed code, web e2e, Lighthouse CI, Reassure, volume, visual,
the Android app on the Android Emulator with Maestro (KVM enabled, 2-core Linux machines with
hardware acceleration since 02/04/2024), reverse tests and the dependency check on a schedule.

No macOS machines in CI, no EAS Workflows, no paid real-device service. A public
repo runs for free; a private repo has 2.000 minutes per month, so the scheduled suites are split into
cadences to fit within that number, and any suite that does not fit runs only in `pnpm verify`.

Three cadences, as built in `.github/workflows/check.yml` (FE-27; machine `ubuntu-24.04`, each job
only calls `pnpm verify` or `pnpm canary`, and uploads `reports/verify.md` as an artifact):

- On every push: the fast group, `pnpm verify --only tokens,types,lint,language,format,deadcode,tooling,trace,unit`
  (static checks, language, dead code, tooling, traceability, unit and component tests on four platforms, data contracts),
  capped at 30 minutes.
- On every pull request: all gates (`pnpm verify`, installing Chromium and WebKit for `gate:web`), capped at 90 minutes;
  `gate:native` exits with the reason "macOS only" and records `skipped (macOS only)`. Mutation testing runs on the
  changed source files against the base branch (`MUTATION_BASE`, `scripts/mutation.mjs`), plus the source next to each
  changed test; a changed shared helper adds the sources of every test that loads it, a changed setup file or
  `jest.config.js` adds the sources of every test. If the part added because of that shared code exceeds 20 sources
  (`BUDGET`), CI leaves it out and the gate's row records the reason: rerun it on the Mac with
  `pnpm verify --only mutation --append`.
- Weekly (Monday, 02:17 UTC) or triggered by hand: the dependency check (`pnpm verify --only deps`) then every
  reverse test (`pnpm canary all`).

Full mutation testing does not fit GitHub's runners and the minutes above, so following the sentence "any suite that does not fit runs only
in `pnpm verify`" it runs in `pnpm verify` on the Mac. The items of the list at the head of this section that are not yet in
CI because they are not built: Lighthouse CI, Reassure, volume, visual (comparing screenshots with baseline images, the "Visual" suite of
section 9.2), the Android app on the Android Emulator with Maestro, Edge and Firefox.

### 11.2 The Mac: `pnpm verify` before sending a pull request

- Runs every gate that CI runs, plus the part only macOS can do: real Safari on macOS and on the
  iOS Simulator, building the iOS app with Xcode, Maestro flows on the iOS Simulator.
  As built (FE-27): the gate `gate:native` (`apps/metis/scripts/native-gate.mjs`) builds the iOS app
  with Xcode and runs the Maestro flows on the iOS Simulator. It copies the app to a build folder outside the repo
  (`~/metis-run/native/apps/metis`, or `NATIVE_DIR`), only runs `pnpm install` and
  `expo prebuild --clean --platform ios` when a native input changes (`app.json` and the files it names,
  `plugins/`, `dependencies`, the lockfile and the pnpm settings), builds the Release build for the iOS Simulator
  (the JavaScript bundle is already inside the app so Metro is not needed; the mock server is on), boots the simulator
  `iPhone 18 Pro` of the newest runtime that has it, installs the app, runs the two flows `e2e/native/smoke.yaml` and
  `e2e/native/phone.yaml` (the Vietnamese labels and the sample project id are read from the source code, passed with `-e`), then shuts down
  the simulator whatever the result; the JUnit report and screenshots are in `reports/native-gate/`. Outside
  macOS the gate exits with code 78 and `pnpm verify` records `skipped (macOS only)`, neither green nor red. Real Safari
  on macOS and on the iOS Simulator is not built yet (section 8.3 and section 13).
- Ends with a report: one green or red line per gate, with the commit id; if a gate is red it
  exits with a code other than 0.
  As built: `pnpm verify` keeps a machine record `reports/verify.json` and redraws `reports/verify.md`
  from it on every run, so no hand-written paragraph survives to the next run. Each row records the gate, the result
  (`green`, `RED` or `skipped (macOS only)`), the number of seconds, the number of tests passed, red, skipped (gates `unit` and
  `web`) or the scope and the mutation score (gate `mutation`), and the mark of the code tree it ran on (a hash of the files
  git would commit in the app and `brand/`, plus the number of uncommitted changes); the head of the report records the commit id, `Tree:`, `All rows on one tree`, `Not run`, and a `Mutation:` line when there is mutation
  testing. A `RED` row exits 1; a run of every gate that cannot name the code tree also exits 1.
  `pnpm verify --only <gate>[,<gate>] --append` reruns a few gates and adds rows under `Reruns`.
- The `--publish-status` flag attaches the status "checked on macOS" to exactly that commit on GitHub;
  the branch protection rule requires this status before merge; if the commit changes it must be run again.
  Not built yet: this flag waits for the repo and the GitHub account of metis (section 13).

### Final notes (FE-27, code cleanup 10/10/2026)

The code cleanup fixed every finding of the code review of 09/10/2026 (`plan/2026-10-10-frontend-code-cleanup.md`).
The sections below were corrected in place to match what was built; the code conventions are in
`apps/metis/CONTRIBUTING.md`. No approved requirement was dropped: what is not built is stated as not built.

- Section 3.1: `src/shell/` gains the role of the part shared by every screen (`useApi`, `problemOf`, `StateView`,
  the shared `states` block) next to the shell; the screen folder now also lists `model.<part>.ts` and `strings/index.ts`; a
  screen does not import another screen, a new shared helper needs two call sites, a route file only hands over URL parameters.
- Section 3.2: the boundary table was rewritten to match what ESLint enforces. The old row 1 (`src/core/` and every `model.ts`
  do not import `src/shell/` or `src/screens/`) was wrong against the code: the model of a screen may import the files
  `model.*` and `strings/` of its own, the model of the shell may import `./strings`. New rows: UI packages are banned also through
  `import()` and `require`, `globalThis` and `self` are additionally banned; the model of a screen does not import `src/shell/`;
  `src/shell/`, `src/screens/`, `src/app/` do not import `src/mocks/`; only `Text.tsx` and `Glyph.tsx` of the
  design system import `Text` of `react-native`. How it is enforced and the reverse tests are recorded.
- Section 3.5: the project header is its own contract `projectHeaderSchema`; every contract of a project page
  extends `projectPageSchema` (the time zone together with the header), so each tab draws its own header; a person's initials
  are sent by the server; the values of the drill-down filter contain no comma.
- Section 5.5: `strings/index.ts` with `STRINGS` and `SAME_IN_VI`; the shared `states` block of the dictionary of the shell;
  sentences are templates with placeholders (`interpolate`, `plural`, `joined`), lint bans assembling sentences in models and hard-coded
  text in components; the dictionary test driven by a registry list; the steps for adding a language were rewritten
  as built (adding `NATIVE_NAMES`, the `STRINGS` record of each `strings/index.ts`, the list in
  `public/index.html`).
- Section 9.4 (new): test layers, the retyped-text rule `local/no-restated-literals`, the language gate
  `gate:language`, the rule that no test is switched off and the guard of browser specs, the scope of `gate:trace`
  per screen (clarifying rule 5 of section 9.1 and the FE-24 note above), the exact floor of the test count.
