# Troubleshoot the core

Each row is a trap that plan one, two or three measured while it built the core in `metis-backend`, with its cause, the fix and the source. The fix names what to run, or what the code does now so that the trap stays closed. Unless a row says otherwise, the measurement was made on the owner's Mac (arm64, ten cores, macOS on Darwin 25.6.0, Docker Desktop 29.4.3) on 14, 15 or 16 Oct 2026, and the source cell is the citation. Run every command from the root of a `metis-backend` clone. None of this code is committed yet, so the page stays a draft until it is on `main`.

How the build and the checks work is in [Develop the core](develop.md).

## Tracing a symptom

Every error answer of the core is Problem Details with a `correlationId`, the id the core gave the request. Every log line of that request carries the same id as `requestId`, and the tenant of the token as `tenantId`, in JSON on standard output (`logging.structured.format.console: ecs`). The line of a 500 carries the type and the frames of the exception and of each cause, never a message, and the driver leaves the detail of the server out of its messages, since a message of PostgreSQL can hold a value of a row. So take the `correlationId` of the answer and find its `requestId` in the log of the core: `docker compose --env-file "$METIS_STACK_ENV" --file stack/compose.yaml logs core` in the local stack. Each request also ends with one line, `served <method> <route> with <status>`, which names the pattern of the route and never the path, since a path holds the ids of records.

Sources: `RequestFilter`, `Problems`, `ProblemAdvice` and `TenantLogFilter` of `core/src/main/java/dev/metis/core/platform/` and `core/src/main/resources/application.yml` of `metis-backend`; [plan two](../../history/plans/2026-10-14-backend-platform-plan.md#review-round-one), line 16227.
